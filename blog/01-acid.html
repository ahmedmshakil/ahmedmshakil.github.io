ACID Properties

The four guarantees that make database transactions reliable and trustworthy.

01 — The Four Pillars

What ACID actually means

Every time your bank transfers money, books a flight, or places an order — ACID properties ensure the operation either fully succeeds or leaves absolutely no trace. They are the safety net of relational databases.

A
Atomicity
All or Nothing

A transaction is treated as a single unit. Either ALL operations succeed together, or NONE of them are applied. No partial updates — ever.

C
Consistency
Rules Always Hold

A transaction brings the database from one valid state to another. All constraints, rules, and triggers must be satisfied before and after.

I
Isolation
No Interference

Concurrent transactions don't see each other's intermediate states. Each transaction runs as if it's the only one — even when thousands run in parallel.

D
Durability
Committed = Forever

Once a transaction commits, it stays committed — even if the server crashes immediately after. Written to disk, not just memory.

Transfer ৳500 from Alice (৳1000) to Bob (৳200). Server crashes after deducting from Alice but before adding to Bob:

① BEGIN TRANSACTION
② UPDATE accounts SET balance = 500 WHERE user='Alice' ✓
③ 💥 SERVER CRASH — Bob not credited yet!
④ ROLLBACK — Atomicity kicks in: Alice gets her ৳500 back
⑤ Database restored to original state. No money lost.
BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE user = 'Alice';
UPDATE accounts SET balance = balance + 500 WHERE user = 'Bob';
COMMIT; -- only if BOTH succeed

Consistency ensures rules are never broken. Alice has ৳100 and tries to send ৳500:

① Rule: balance cannot go below ৳0
② UPDATE: Alice balance = 100 - 500 = -400 ← VIOLATES constraint!
③ CONSTRAINT VIOLATION — transaction rejected
④ Database stays consistent: Alice still has ৳100
-- Constraint defined at table creation:
CREATE TABLE accounts (
  balance DECIMAL CHECK (balance >= 0) -- consistency rule!
);
-- Any transaction violating this is auto-rejected

Two people read Alice's balance simultaneously and both try to deduct ৳500:

① TXN-1 reads Alice balance: ৳1000
② TXN-2 reads Alice balance: ৳1000 (same — TXN-1 not committed)
③ Without isolation: BOTH deduct ৳500 → Alice ends up with ৳500 but sent ৳1000!
④ With isolation: TXN-2 waits for TXN-1 to commit, then reads ৳500 → correctly rejected
-- Isolation levels (strictest to loosest):
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE; -- full isolation
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED; -- most common
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED; -- dangerous

Transaction commits successfully, then power goes out 1 second later:

① COMMIT received — write to WAL (Write-Ahead Log) on disk ✓
② Success response sent to user ✓
③ 💥 POWER OUTAGE — server goes down
④ Server restarts → replays WAL log → committed data fully restored
-- WAL (Write-Ahead Logging) ensures durability
-- Every committed transaction is written to disk log FIRST
-- On crash recovery, Postgres replays the WAL:
SELECT pg_walfile_name(pg_current_wal_lsn()); -- see current WAL file
03 — Key Concepts

Vocabulary to know

🔄
Core
Transaction

A group of SQL operations treated as one unit. Starts with BEGIN, ends with COMMIT or ROLLBACK.

⏪
Safety
Rollback

Undo all changes from the current transaction. Called automatically on failure, or manually on error.

📝
Durability
WAL Log

Write-Ahead Log — changes are logged to disk before being applied. Enables crash recovery and replication.

🔒
Isolation
Isolation Level

Controls how much one transaction sees others. READ COMMITTED is the default in most databases.
