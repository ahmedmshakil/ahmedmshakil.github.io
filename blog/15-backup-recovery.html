Backup & Recovery

Your last line of defense — point-in-time recovery, WAL archiving, and disaster recovery strategies.

01 — Why Backups Are Critical

Everything fails eventually

Hardware fails, humans make mistakes (DELETE FROM users WHERE without a WHERE clause), ransomware strikes. Without proper backups, data is gone forever. The goal: recover to any point in time with minimum data loss and downtime.

RPO — Recovery Point Objective
⏰ How much data can you lose?

Maximum acceptable data loss measured in time. RPO = 1 hour means you can lose up to 1 hour of data. Drives backup frequency.

RTO — Recovery Time Objective
🚀 How fast must you recover?

Maximum acceptable downtime. RTO = 15 minutes means the system must be back online within 15 minutes of failure. Drives recovery architecture.

02 — Backup Types

📸 Full Backup

Complete copy of the entire database. Slowest to create, fastest to restore. Typically done weekly or daily as a baseline.

∆ Incremental Backup

Only backs up data changed since the last backup. Fast to create, but slower to restore (must replay all increments from base).

📋 WAL Archiving

Ship Write-Ahead Log files continuously to a backup location. Enables point-in-time recovery (PITR) — restore to any second.

🔄 Logical Backup (pg_dump)

Exports database as SQL statements. Portable, readable, schema-flexible. Slower to restore for large databases.

03 — Point-in-Time Recovery

Undo any mistake to the exact second

With WAL archiving, you can restore the database to any point in time — even to 5 minutes before someone ran a catastrophic DELETE.

-- postgresql.conf: enable WAL archiving
archive_mode = on
archive_command = 'cp %p /backup/wal/%f'

-- Take a base backup:
pg_basebackup -D /backup/base -Ft -z -P

-- Restore to specific time (recovery.conf):
restore_command = 'cp /backup/wal/%f %p'
recovery_target_time = '2025-01-10 14:30:00'

-- pg_dump: logical backup
pg_dump -Fc mydb > mydb_backup.dump
pg_restore -d mydb mydb_backup.dump
04 — The 3-2-1 Rule
3️⃣
Rule
3 Copies of Data

1 primary + 2 backups. If one is corrupted or lost, two others remain. Never rely on a single copy.

2️⃣
Rule
2 Different Media

Store on different storage types (SSD + tape, local disk + cloud). One media failure doesn't destroy all copies.

1️⃣
Rule
1 Offsite Copy

At least one backup in a different physical location. Fire, flood, or earthquake in your data center won't destroy all copies.

✅
Critical
Test Your Restores

A backup you've never tested is not a backup. Regularly restore to a test environment and verify data integrity.
