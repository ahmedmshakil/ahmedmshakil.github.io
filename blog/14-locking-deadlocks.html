Locking & Deadlocks

How databases control concurrent access — and the circular waits that can bring everything to a halt.

01 — Why Locking Exists

Concurrent access needs coordination

Without locks, two transactions could read the same value, both modify it, and write back — the second write overwrites the first (lost update). Locks ensure only one transaction modifies a row at a time, preserving data integrity.

Shared Lock (Read)
📖 Multiple readers OK

Many transactions can hold a shared lock simultaneously. None can write while shared locks exist. Used by SELECT ... FOR SHARE.

Exclusive Lock (Write)
✍️ Only one writer

Only one transaction at a time. Blocks all other reads and writes. Held during UPDATE, DELETE, SELECT ... FOR UPDATE.

02 — Deadlock

The circular wait that freezes everything

A deadlock occurs when Transaction A waits for a lock held by Transaction B, while Transaction B waits for a lock held by Transaction A. Neither can proceed — they wait forever. The database detects this and kills one transaction.

TXN-A holds lock on Row 1, waiting for Row 2
TXN-B holds lock on Row 2, waiting for Row 1

→ Circular wait → Deadlock detected → One TXN rolled back
-- Transaction A
BEGIN;
UPDATE accounts SET balance=balance-100 WHERE id=1; -- locks row 1
UPDATE accounts SET balance=balance+100 WHERE id=2; -- waits for row 2...

-- Transaction B (simultaneously)
BEGIN;
UPDATE accounts SET balance=balance-50 WHERE id=2; -- locks row 2
UPDATE accounts SET balance=balance+50 WHERE id=1; -- waits for row 1 → DEADLOCK
03 — Prevention & Solutions
🔢
Best Fix
Consistent Lock Order

Always acquire locks in the same order (e.g., always lock lower ID first). If all transactions agree on order, circular waits can't form.

⏱️
Safety Net
Lock Timeout

Set a timeout: if a transaction waits too long for a lock, abort and retry. Prevents indefinite blocking even without deadlock detection.

👁️
Modern
MVCC (Optimistic)

Multi-Version Concurrency Control — readers don't block writers. Each transaction sees a snapshot. Postgres uses MVCC by default.

🔄
App Layer
Retry on Deadlock

When deadlock is detected, the DB rolls back one transaction. Your application should catch this error and retry the transaction.
