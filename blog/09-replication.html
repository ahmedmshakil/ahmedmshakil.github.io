Database Replication

Copying data to multiple servers for high availability, disaster recovery, and read scalability.

01 — The Idea

Keep identical copies on multiple servers

Replication keeps one or more database servers in sync with a primary server. If the primary fails, a replica can take over immediately. Replicas also serve read traffic, spreading the load across multiple servers.

WRITES → Primary (Leader)
        ↓ replicate
┌──────────────────────┐
Replica 1    Replica 2    Replica 3
(read)       (read)       (failover)
02 — Types of Replication

📡 Synchronous

Primary waits for replica to confirm write before returning success. Zero data loss. Slower — every write waits for network round trip to replica.

📤 Asynchronous

Primary commits immediately, sends changes to replica in background. Fast writes. Risk: brief window of data loss if primary crashes before replica catches up.

🔄 Semi-synchronous

At least one replica must acknowledge before commit. Balance between safety and performance. Used by MySQL by default.

🌍 Multi-master

Multiple servers accept writes. Complex conflict resolution needed. Used in active-active geo-distributed setups (CockroachDB, Cassandra).

03 — Key Concepts
⏳
Challenge
Replication Lag

Async replicas can fall behind the primary. A user writes data then reads from a replica that hasn't caught up yet — stale read.

🔄
Recovery
Failover

When primary fails, a replica is promoted to primary. Automatic failover (with tools like Patroni) can happen in seconds.

📊
Scale
Read Scaling

Route all SELECT queries to replicas. Primary handles only writes. 3 replicas = 3x read throughput.

💾
Safety
Disaster Recovery

Keep a replica in a different data center or region. If the entire primary data center burns down, the replica survives.
