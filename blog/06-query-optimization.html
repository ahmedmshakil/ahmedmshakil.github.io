Query Optimization

How databases plan and execute queries — and how to make them dramatically faster.

01 — The Idea

The database makes a plan before running your query

When you run a SQL query, the database doesn't just execute it blindly. The Query Planner analyzes all possible ways to retrieve the data, estimates the cost of each, and picks the cheapest plan. Understanding this lets you write queries that are orders of magnitude faster.

Without Optimization
⏳ Slow Query

A query that does a full table scan on 10 million rows, joins without indexes, selects unnecessary columns, and runs subqueries in a loop.

With Optimization
⚡ Fast Query

The same result using indexes, proper join order, covering indexes, and avoiding N+1 problems. Can be 1000x faster on the same data.

02 — EXPLAIN ANALYZE

Your most important tool: EXPLAIN

EXPLAIN shows the query execution plan. EXPLAIN ANALYZE actually runs it and shows real timings. This is how you find slow queries.

EXPLAIN ANALYZE
SELECT u.name, COUNT(o.id) as order_count
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.country = 'BD'
GROUP BY u.id;

-- Output tells you:
-- Seq Scan = full table scan (BAD for large tables)
-- Index Scan = using an index (GOOD)
-- Hash Join / Nested Loop = join strategy used
-- rows=1000 actual rows=1 → bad estimate, consider ANALYZE
03 — Optimization Tips

Practical rules for faster queries

🔍
Rule 1
Use indexes on WHERE columns

Every column in a WHERE, JOIN ON, or ORDER BY clause is a candidate for indexing. Check EXPLAIN for Seq Scans.

📊
Rule 2
SELECT only what you need

Avoid SELECT *. Fetch only the columns you need — reduces data transfer and enables covering indexes.

🔄
Rule 3
Avoid N+1 queries

Don't query inside a loop. Use JOINs or batch queries to fetch all data in one round trip instead of N+1.

📈
Rule 4
Run ANALYZE regularly

ANALYZE updates the query planner's statistics about data distribution, helping it make better execution plans.

🧩
Rule 5
Use covering indexes

An index that includes all columns needed for a query lets Postgres answer from the index alone — no table read needed.

⚠️
Anti-pattern
Avoid functions on indexed columns

WHERE LOWER(email) = 'x' can't use an index on email. Use a functional index or store data in the right case.
