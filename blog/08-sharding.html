Database Sharding

Splitting one massive database horizontally across multiple servers for unlimited scale.

01 — The Problem

When one database isn't enough

A single database server has limits — CPU, RAM, disk throughput. When your app has 500 million users, no single machine can handle it. Sharding splits the data horizontally: User IDs 1–10M go to Shard 1, 10M–20M to Shard 2, and so on. Each shard holds a subset of the data.

02 — Sharding Strategies

🔢 Range Sharding

Split by value ranges. User IDs 1-1M → Shard 1. Simple to understand. Risk: hotspots if recent IDs get all traffic.

#️⃣ Hash Sharding

shard = hash(user_id) % num_shards. Distributes evenly. No hotspots. Drawback: range queries span multiple shards.

🗺️ Directory Sharding

A lookup table maps each key to its shard. Flexible, but the directory itself becomes a bottleneck.

🌍 Geo Sharding

Route users by geography — BD users to Asia shard, EU users to Europe shard. Reduces latency and meets data residency laws.

03 — Challenges
🔗
Hard
Cross-shard Joins

Joining data across shards requires fetching from multiple databases and merging in application code. Very expensive.

📊
Hard
Rebalancing

Adding a new shard means moving data around. This is complex and risky — data must be migrated without downtime.

🔢
Hard
Auto-increment IDs

Each shard generates its own IDs. Use UUIDs or a global ID service (like Twitter's Snowflake) to avoid collisions.

🔄
Alternative
Consider First

Before sharding: optimize queries, add indexes, scale vertically (bigger server), use read replicas. Sharding is a last resort.
